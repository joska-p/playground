# Documenting a Package

Every package in `packages/*` automatically receives documentation. Each package has a `typedoc.json` extending the shared base; packages with a public API add `entryPoints` (from `package.json` exports), while readme-only packages use `"entryPoints": []`.

A package's documentation has two halves, each maintained where it lives:

- **The README** (`packages/<name>/README.md`) — the concept: what the package is, why it exists, quick start, usage examples, gotchas. Its YAML frontmatter is the source of truth for the package's title, description, and whether it ships an app.
- **The API reference** — generated by TypeDoc from **TSDoc comments** on exported symbols, rendered as anchored modules on the package's page.

---

## 1. Write the README

Keep the README focused on concepts that do not change with every refactor:

- `# @repo/<name>` title and a `> ` one-liner tagline.
- **Purpose** — why this package exists.
- **Quick Start** — install + first minimal example.
- **Usage Examples** — real-world snippets.
- **Patterns & Gotchas** — design decisions and pitfalls.

The README frontmatter is minimal — nothing else is allowed:

- `title` — the display name.
- `description` — card and page text (keep it ~160 characters or fewer).
- `hasApp` — `true` only when the package ships a real, demonstrable React app.

`package`, `kind`, and `module` are injected by the build pipeline at generation
time; they never live in the README.

---

## 2. Document the code with TSDoc comments

Add TSDoc/`/** ... */` comments to exported symbols:

- One-liner for functions, classes, and types.
- `@param` / `@returns` for non-obvious signatures.
- `@example` for tricky usage.
- `@internal` to hide internals, `@deprecated` to mark removals.

---

## 3. Generate documentation and project pages

From the repository root, run:

```bash
pnpm build-docs
pnpm gen:project-pages
```

- `pnpm build-docs` (`scripts/build-docs.mjs`) runs TypeDoc once per package and writes `.mdx` files into `apps/playground/.generated/api-docs/<package-dir>/` — a `README.mdx` overview per package plus one file per module. A custom content loader (`apps/playground/src/content/loaders/api-docs.ts`) serves them as the `api` collection.
- `pnpm gen:project-pages` reads the generated docs and generates a static Astro page at `/discoveries/<package-dir>/` for every package. It never overwrites an existing page — prefer writing discovery pages by hand.

No `index.json` or per-package route config is involved — the collection is the single source of truth.

---

## 4. Viewing your documentation

- `/discoveries/<package-dir>/` — the application showcase (when `hasApp` is `true`), the README overview, and the API navigation.
- API modules are rendered as sections on the same page, anchored at `#overview` (README) and `#<module-path>` (e.g. `#core-Camera` for `core/Camera`), and linked from the sidebar.

The URL is always derived from the package name (`<name>` with the `@repo/`
prefix stripped) — `title` and the URL are fully decoupled, so a package can be
renamed in its frontmatter without moving its page.
